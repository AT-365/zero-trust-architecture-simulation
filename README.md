# Zero Trust Architecture Simulation

[![Tests](https://github.com/AT-365/zero-trust-architecture-simulation/actions/workflows/tests.yml/badge.svg)](https://github.com/AT-365/zero-trust-architecture-simulation/actions/workflows/tests.yml)

A tested Python security prototype that simulates a zero-trust access control policy engine. Every access request is evaluated against seven independent control vectors: identity verification, account status, role-based authorization, device ownership, device posture and compliance, risk assessment, and network micro-segmentation policy.

**Project Scope:** This is an intentionally controlled academic prototype demonstrating zero-trust policy logic and decision monitoring. It is not a production identity platform, network access control system, or SIEM deployment.

## Why This Project Matters

- designing policy decision engines with multiple orthogonal control vectors
- implementing identity and access management logic
- building device trust evaluation systems

- prototyping security architecture before live deployment

- documenting security decisions and trade-offs clearly
- connecting theory (zero trust principles) to code (policy engine)

## Project Overview

Zero Trust Architecture is a security model that operates on the principle "never trust, always verify." Instead of assuming users and devices inside a network are trustworthy, every access request is evaluated against multiple security criteria:

1. **Identity verification** - Is the user known and active?
2. **Role-based access control** - Does the user's role permit access to this resource?
3. **Device trust** - Is the device owned by the organization, managed, compliant, and encrypted?
4. **Risk assessment** - What is the current risk score of the device and network segment?
5. **Resource sensitivity** - How sensitive is the requested resource?
6. **Micro-segmentation** - Is the source network segment approved for this resource?
7. **Continuous monitoring** - Are access denials and repeated failures being tracked?

This repository demonstrates each of these controls in executable Python code with structured test scenarios.

## What the Simulation Demonstrates

- **Identity verification:** Unknown users and inactive accounts are denied access.
- **Least privilege:** Users must have roles explicitly authorized for the requested resource.
- **Device trust evaluation:** Device ownership, management status, compliance status, encryption, and risk level are all considered independently.
- **Micro-segmentation enforcement:** Source network segments are approved per resource; access is denied if the segment is not authorized.
- **Continuous monitoring:** Every policy denial is logged. Repeated denials from the same user/device trigger escalated severity alerts.
- **Evidence-based decisions:** Every access scenario produces a CSV record showing the request, the controls evaluated, the decision made, and the reason for that decision.


Inspect the decision output:

```bash
cat results/access_log.csv
cat results/alerts.csv
```

## Architecture

Zero Trust policy decisions flow through multiple independent checks:

```mermaid
flowchart LR
    A[Access request] --> B[Policy decision point]
    B --> C{Identity and role}
    C --> D{Device posture and risk}
    D --> E{Resource and segment}
    E --> F[Allow or deny]
    F --> G[Decision log]
    F --> H[Alert monitor]
```

**Decision flow:**
1. Verify user identity and account status
2. Check role authorization for the resource
3. Evaluate device trust (ownership, compliance, encryption, risk)
4. Validate network segment for this resource
5. Log the decision (allow or deny)
6. If denied, generate or escalate alert

See [`docs/architecture.md`](docs/architecture.md) for detailed policy flow and component mapping.

## Project Context

This project was completed for **CSCI 7536 — Network and Computer Security** at Georgia Southern University. It combines:

- **Academic policy design:** Zero trust principles and security architecture theory
- **Practical implementation:** Python policy engine with decision logic
- **Lab validation:** Azure-hosted Ubuntu VM with real security configuration
- **Network evidence collection:** SSH hardening, controlled traffic generation, packet capture with tcpdump and Wireshark, network scanning with nmap

The public repository preserves the policy simulation and synthetic test evidence. It does not include credentials, SSH keys, cloud account details, real IP addresses, or raw packet captures (kept private to protect infrastructure details).

## What I Learned

This project taught me important lessons about security architecture and policy design:

- **Zero trust requires defense in depth across multiple vectors.** No single control is sufficient; identity, device trust, role, risk, and segmentation must all work together. A denial at any checkpoint prevents access.

- **Lab evidence is essential for credibility.** Building the policy logic is one thing; showing it works on real Azure/Ubuntu infrastructure with actual SSH hardening, traffic capture, and network scanning makes the project concrete and verifiable.

- **Alert escalation and monitoring matter as much as initial decisions.** The policy engine must track repeated failures and escalate severity. A single denial is noise; repeated denials from the same user/device is a security event.

- **Academic prototypes clarify concepts but need hardening for production.** This simulation works well for demonstrating zero trust logic. Production deployment would require integration with live identity providers, real endpoint compliance data, and centralized SIEM systems.

- **Structured testing catches policy bugs.** The 13 test scenarios revealed edge cases I would have missed without systematic validation. Every decision path should be explicitly tested.

## Scope and Limitations

- **Synthetic data:** Users, devices, resources, and requests are statically defined, not live directory data
- **Policy attributes only:** MFA, TLS, and device posture are represented as policy variables, not integrations with actual auth systems or endpoint management platforms
- **Monitoring prototype:** The alert engine detects denials and escalates repeated failures; it is not a full SIEM or behavioral analytics platform
- **Infrastructure details withheld:** Azure and Ubuntu configuration is summarized; identifying details are private

## Suggested Next Steps

To move this prototype toward production:

- Integrate a real identity provider (Okta, Azure AD, or similar) with short-lived credentials
- Consume live endpoint-compliance signals from Mobile Device Management (MDM) systems
- Centralize protected logs and alert routing to a SIEM platform
- Add risk-based and time-aware access rules (e.g., deny access outside business hours or from geographic anomalies)
- Map logical policies to network enforcement controls (firewalls, network ACLs, micro-segmentation appliances)
